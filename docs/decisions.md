# 产品决策与取舍

更新时间：2026-10-13，版本 0.3.4。

这里汇总刻意没做、或刻意只做一半的功能：为什么不做，代价是什么，什么情况下值得重新考虑。
有些决定来自 [与 dsh-context 的对比](dsh-comparison.md) 和 [侧栏设计](sidebar-design.md)，这里只留结论；数据口径细节见 [架构](architecture.md)。

四条总原则决定了下面大多数取舍：

- **只读**：插件只观察，不改变 ZCode 的行为、设置、数据库或权限。
- **离线**：不联网、不调用模型，所有数据留在本机。
- **有证据才下结论**：数据缺失时显示“未知”或“无法得知”，不用推测填满界面。
- **窄而专**：面板是单个会话侧栏里的一个 Tab，只服务“哪一步变大、多了什么、点开看正文”这一条路径。

## 只读与权限

**不自行授权两个只读工具，也不使用通配授权。**
ZCode 对插件的 MCP 工具照常执行权限规则，`readOnlyHint` 不会免除审批。插件写数据库或配置给自己放行，就越过了用户的权限决定。
代价：首次使用要用户手动允许两个工具；实测宿主的审批入口不在主页面显示，面板会一直“读取中”直到超时，只能靠 README 和页面提示引导。
重新考虑：ZCode 提供插件声明只读工具的官方机制，或修复审批入口的显示。

**不把 CLI 的 `permission.allowedTools` 当作安装方案。**
在 Desktop 会话里实测它没有放行详情工具，不能写成已验证的解法。

**不自动打开“完整保留模型 I/O”。**
这个设置会增加磁盘占用，而且改的是 ZCode 的行为。插件只说明它能解锁哪些功能，由用户自己决定。
代价：默认设置下看不到移除项、按类别的变化量和正文 Diff。

**不修改系统提示词（不做 dsh 的 Prefix/Suffix 设置）。**
它会改变 Agent 的行为，超出只读观察的范围。

**视图状态只是偏好，不提供授权。**
每次工具调用都重新从宿主元数据绑定会话。保存的选择、展开状态即使指向别的会话，也不会被用来读取数据。

## 数据真实性

**不显示实时上下文占用或上下文窗口百分比（不做 dsh 的 Live / Next Request）。**
插件读的是已经落盘的请求记录，最新一条也只是上一次请求，不是下一次请求的实时状态。把它改名成“当前上下文”会误导用户。
重新考虑：ZCode 向插件提供上下文压力或组成的实时投影。

**不猜内容来源（skill、插件、注入）。**
只按 system、user、assistant、tool、schema 这些角色分类。按正文片段拆来源一定会有错判，而错判比“未细分”更难被发现。
重新考虑：记录里出现结构化的来源元数据。

**不从内容变少推断压缩。**
压缩只以日志事件为准；大小下降只作为观察到的变化显示。只读最近 3 天的日志，所以“没读到事件”也不代表没有压缩。

**上下文事件以 ZCode 会话记录（SQLite 的 `message` / `part` 表）为准，日志只补它没有的类型。**
会话记录覆盖整个会话，不受日志 3 天窗口、请求记录 24 MiB 读取窗口和 32 MB 缓存的限制。每条消息带 ZCode 自己写的 `semantics`（来源、类型、是否发给模型），所以注入按 ZCode 的标签显示（TodoWrite 提醒、Agent 列表、恢复的上下文、后台任务通知等），不按正文猜来源。
- 注入：模型可见、但不是用户自己发的消息，每条一行；Skill 加载来自 `tool` 部分。
- 压缩：来自 `compaction` 和 `timeline` 部分，带压缩前后 token、被摘要的消息数和摘要消息；同一次压缩的日志按命令 ID 或时间重叠去掉。
- 模型切换：来自 `timeline` 的 `model_change`；有它时不再用日志里的模型更新。
- 回退、编辑提问和 MCP 工具注册只在日志里，仍按 3 天窗口读取。
读取只限当前绑定会话，内容和插件已经在读的请求记录是同一份；只用 `json_extract` 取需要的字段，大的工具输出不进 JavaScript。按 `time_updated` 增量读取，行数变少（回退删除）时整体重读。读不到这两张表时退回到只用日志。
普通的工具调用和结果不单独成为事件：它们已经在概览的「输入」行和「仅变化」里。0.3.5 之后一度按请求记录推断“注入”和“大块内容”，换成会话记录后去掉：推断只能覆盖缓存里的几步，大块内容回答的是趋势图已经回答的问题。

**事件按原文定位到浏览器里的那一项，定位不到就显示原文。**
注入在它之后的第一个主请求里找：Skill 按工具调用 ID，其他按原文完全包含（取最后一处，因为提醒会重复），不做相似度匹配。找不到对应请求或里面没有这段原文（请求记录已轮转、超出读取窗口、更早的历史未加载）时，事件不指向任何一步，点击直接展开会话记录里的原文，不把邻近的一步当成它。
压缩选中之后的第一步、以之前的一步为基线：能对比时切到「仅变化」；不能对比时写明原因并打开 ZCode 的续接摘要。被摘要的内容从会话记录按需读取，按提示、回复、思考、工具调用逐项列出——默认记录（tail）下这是唯一能看到“压缩去掉了什么”的地方。模型切换打开请求概览；MCP 工具注册在工具定义里筛出 `mcp__` 工具。早于已加载步骤的事件先加载更早的步骤再定位。

**不强行把 SQLite 用量和请求记录逐条对应。**
`logical_request_id` 和记录里的 `requestId` 没有被证明是同一个标识，硬连可能按网络重试次数把用量算多。两者分成“用量页”和“请求诊断”两条轨道，同一条记录里自带的 provider usage 作为这次 attempt 的实际用量单独显示。

**默认记录（tail）下不猜移除了什么。**
ZCode 默认只记录每次请求最近 64 条消息。新增内容可以由入场标记推出，移除项无从得知，界面直接说明，不做对比。

**普通消息的替换不做正文 Diff。**
只有工具结果 ID 或 schema 名称唯一时才配对“替换前 / 替换后”。按文本相似度或位置配对，很容易把两条无关消息说成同一条的修改。

**已淘汰或轮转的内容不恢复，脱敏图像不显示缩略图。**
只展示真实保留下来的内容。

**步序号是相对的；入场标记追不到时显示“更早”。**
序号从当前能读到的第一条记录开始数。遇到记录缺口、文件重置或压缩时不往前猜步骤。

**工具调用次数读不到时显示未知，不显示 ×0。**
×0 的意思是“确认从未调用”，这是可以据此删除工具定义的结论，不能用来表示数据缺失。

**不估算费用。**
需要按版本维护模型价格、别名和计费口径，还要联网更新。价格不明时报出的数字是假的。

## 估算口径

**不内置分词器，token 数用按文字类型加权的估算。**
不同模型的分词器差别很大；内置多个分词器会显著增大离线包，而且结果依然只适用于部分模型。估算用于比较大小和变化，所有估算值都带“≈”。
0.3.4 起，英文和代码约 4 字符 ≈ 1 token，中日韩文字约 1.5 字 ≈ 1 token；之前一律按 4 字符计，中文内容显得偏小。

**不用实际输入按比例缩放各类别的估算。**
默认记录下，实际输入里包含没有被记录的更早消息。按比例缩放，会把这部分大小摊到已记录的类别上，同时把“估算”伪装成“实测”。现在的做法是把差额单独显示为“更早消息（未记录）”。
重新考虑：完整保留的会话足够多，可以先验证估算与实际输入的比例是否稳定，再提供一个明确标注的校准值。

## 读取范围与性能

**所有读取都有上限，超出部分不可见。**
冷读文件窗口 24 MiB，单次扫描和单行各 8 MiB；每个文件缓存 120 条记录，最多 8 个会话、合计 32 Mi 字符；worker 堆 256 MiB。趋势每页 60 条，最多往前翻 4 页；正文每块 12k 字符，正文查找最多导航 100 处；用量页为 30 天、时间线 80 条。
代价：超长会话的早期历史看不到。换来的是插件在任何会话上都不会拖慢 ZCode 或耗尽内存。

**正文 Diff 是“共同前后缀之间的替换块”，不是最小行编辑序列。**
线性时间、有上限；最小 LCS Diff 在大工具结果上开销不可控，侧栏里也难以阅读。

**复制只复制当前这一块；Markdown 只支持标题、段落和代码。**
捕获内容一律按纯文本或受限 Markdown 显示，不执行其中的 HTML。

**服务端不缓存无变化的读取（0.3.4 实测后放弃）。**
32 MiB 的真实会话，无变化时一次刷新约 7 ms，其中 SQLite 约 4 ms。按文件修改时间缓存会引入读到过期用量的风险，收益只有几毫秒。

**超时的读取如果已经在执行，就让它跑完，不重启 worker。**
重启会丢掉解析缓存，下一次冷读可能再次超时，形成循环。还没开始执行的读取则直接跳过。

**用轮询，不用推送。**
面板只能主动调用 app-only 工具读取数据，目前没有验证过宿主有可用于此的推送通道。0.3.4 起数据无变化时逐步放慢到 10 秒，面板可见、获得焦点或鼠标移入时立即刷新。

## 面板形态和尺寸

上下文面板是会话右侧面板里的一个 Tab：宽度大约 320–560 CSS px，和其他 Tab 共用同一块区域，而且只属于打开它的会话。
ZCode 的 `fullscreen` 显示模式指的就是这个侧栏，不是中央大页面；请求 `inline` 也不保证有卡片接管。
dsh-context 有一部分功能依赖宽屏的中心页，硬搬进来要么挤坏，要么只剩装饰。下面这些不做，主要原因是面板放不下或用起来不顺，而不是缺数据。

**不做两列布局（趋势和浏览器并列、列表和正文并列）。**
560 px 分成两列，每列不到 280 px，类别行的名称、条数、大小和占比放不进一行。改为单列从上到下：概览、趋势、浏览器、压缩事件。
重新考虑：ZCode 提供经过验证的宽工作区页面。

**正文 Diff 只做单列，不做左右对照。**
前后两段正文各占半宽，长行全部折行，反而更难对比。单列只高亮变化块，前后各留两行上下文。

**不做 DNA 元素条带。**
长会话一次请求有几百个上下文元素，在几百像素宽的条带里每个元素只有一两个像素，看不清也点不中。按类别折叠、按大小排序能更快找到大块内容。
数据上也有限制：记录里的 SDK 消息和 provider 请求体是两种表示，条带顺序不能冒充 provider 收到的原始顺序。

**不做跨会话 Insights（时间范围、热力图、会话卡片、跨会话搜索）。**
这是工作区级的仪表盘，需要中心页的面积；而这个 Tab 属于单个会话，在一个会话的侧栏里展示别的会话也不符合预期。
读取整个工作区还需要显式扩大读取范围，不能借当前会话的绑定静默读取。

**不做子代理网络图（dsh 的 Fleet）。**
节点关系图在窄栏里放不下，标签会互相重叠。父子会话将来可以用列表展示，前提是先设计好授权范围；实时运行状态目前没有验证过的来源。

**不做时间组成图和时长曲线。**
等待、生成、工具、开销的分段条再加更细的生成阶段，在窄栏里层层堆叠，密度过高；趋势区已经有总量 / 变化、步骤 / 轮次两组切换。
数据上也有缺口：并行工具的耗时不能直接相加成墙钟时间，没有流式阶段数据就拆不出思考和正文耗时。用量页只列每次请求的耗时。

**不做额外入口（中心页、/context 命令、偏好设置卡）。**
ZCode 给插件的界面入口就是会话侧栏的 Tab；dsh 的一级导航和命令入口在 ZCode 里没有对应的可调用接口。少数偏好直接放在用到它的地方，比如趋势上的切换按钮。

**趋势只铺开最近一屏可点击的柱子。**
不把整个会话压成一排点不中的细线；更早的步骤横向滚动或翻页查看，「自适应」纵轴按可见范围缩放。

**顶部不堆累计用量卡片，会话 ID 不常驻一行，解释性文字收进底部说明。**
窄栏的第一屏只有几百像素高，要留给“这一步多大、变了什么”。

## 主路径和信息密度

面板只服务一条主路径：哪一步变大了、多了什么内容、点开看正文。帮不上这个问题的功能，即使有数据也不放进来。

**只保留一种布局。**
0.2 有“诊断优先 / 浏览优先”两种布局偏好，0.3.0 重写侧栏时去掉了浏览优先。卡片布局里的趋势足够紧凑，浏览器紧跟在后面；第二种布局的收益抵不过它带来的成本：每种宽度、主题和语言都要多验证一遍。

**条目在列表里行内展开，不跳到单独的详情页。**
0.2 点开条目会进入详情页，靠“返回”回到列表。0.3.0 改成行内展开：读正文时仍能看到它属于哪个类别、前后是什么，也不需要来回恢复滚动位置。

**首页是请求诊断，30 天累计用量放到次级页面。**
累计数字回答不了“为什么这么大”。

**标题生成、压缩等辅助请求不进趋势。**
它们仍可在下拉框里选中，但混进趋势会让变化柱和相邻柱没有可比性。

**展开条目阅读时暂停跟随最新请求。**
新请求到来只提示“有 N 个新请求”，不会把正在读的正文切走。

## 暂缓：缺数据或证据

下面这些放得进面板，也在主路径附近，卡在数据是否可信：

| 功能 | 暂缓原因 |
|---|---|
| 文件活动（读、写、搜索过的文件） | 只能基于明确的工具名、参数和结果提取；任意 shell 命令解析不出可靠的文件事实 |
| 工具耗时、错误与重试 | 只能用可信字段，并区分逻辑请求和实际模型调用，避免重复累计 |
| 子代理的独立用量 | session 表有 `parent_id`，但要先确定读取子会话的授权范围 |
