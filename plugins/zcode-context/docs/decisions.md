# 产品决策与取舍

更新时间：2026-10-21，含 0.3.10 之后未发布的改动。

这里汇总刻意没做、或刻意只做一半的功能：为什么不做，代价是什么，什么情况下值得重新考虑。
有些决定来自 [与 dsh-context 的对比](dsh-comparison.md) 和 [侧栏设计](sidebar-design.md)，这里只留结论；数据口径细节见 [架构](architecture.md)。

四条总原则决定了下面大多数取舍：

- **只读**：插件只观察，不改变 ZCode 的行为、设置、数据库或权限。
- **离线**：不联网、不调用模型，所有数据留在本机。
- **有证据才下结论**：数据缺失时显示“未知”或“无法得知”，不用推测填满界面。
- **窄而专**：面板是单个会话侧栏里的一个 Tab，只服务“哪一步变大、多了什么、点开看正文”这一条路径。

## 上下文浏览器的交互规则

浏览器在任何时刻只回答一句话：**请求 R 里，相对基线 B 属于集合 S（全部 / 仅变化）、并满足条件 F 的内容有哪些。**排序、展开、打开哪一项只决定怎么摆，不改变结果。下面五条规则由此而来，新增入口时按它们检查。

**一个操作只改它名字说的那个维度。**
「搜索已加载请求」跨多个请求列出全部匹配，没有单一基线，因此这时不显示「全部 / 仅变化」，而是写明它不适用。
选步骤只改 R，切「全部 / 仅变化」只改 S，输入关键词只改 F，点概览图例只展开并滚动到那一类，点「输入」行的条目只打开它。0.3.6 之前图例和「输入」行会顺手清掉筛选、切回「全部」，用户看不出筛选为什么没了。
代价：被筛选挡住的类别点开是空的，需要用户自己清除筛选——所以筛选框旁边有明确的 × 按钮。

**能点的数字，就等于点开后看到的条数。**
类别标题左半边是结果：「m / n 项」和 `+N −N` 都按当前的 S 和 F 计算，`+N` 本身是按钮，点开正好 N 条。右半边是这一步的事实：大小、占比、和基线相比的 token 变化，永远按整个请求计算，不随筛选变化。「仅变化 +a −r」同理按筛选计数，未筛选的总数放在提示里。所有计数由服务端的 `listing` 一次算出，界面不再在多组字段之间挑选——之前 `+3` 取自未筛选的对比、「1 / 56 项」取自筛选后的列表，于是出现“+3 点开只有一条，而且不是新增的”。

**导航带来的状态和用户自己的状态分开。**
关键词、排序、模式、展开是用户设的，按会话保存，切换步骤后保留。点事件是一次临时的“带你去看”：压缩、回退和 MCP 工具注册进入**事件焦点**，自带基线和条件，在浏览器顶部显示，用户的筛选在此期间暂停（划掉显示）而不是被改写。焦点在点 ×、选别的步骤、输入关键词或换基线时结束，不保存，重新打开面板不会回来。焦点内仍可切换「全部 / 仅变化」，因为它只是同一批内容的两种看法。注入和模型切换只选中那一步、打开那一项，不需要焦点。
代价：多一层状态。选择“暂停”而不是“叠加”：叠加时一个旧关键词会把事件要展示的内容藏起来。

**条件表达真实的意图。**
“这次注册带进了哪些工具”是“工具定义里、工具名以 `mcp__` 开头”，按字段匹配，不是对正文做全文搜索——全文搜索 `mcp__` 会把所有提到 MCP 工具的提醒、回复和工具结果一起筛进来。注册数（日志里的 `registeredToolCount`）包含不发给模型的工具，例如本插件 `visibility:["app"]` 的两个面板工具，焦点栏会写明。

**定位不到就说定位不到，不拿别的一步顶替。**
与注入的规则一致。为了让打开的那一项一定可见，服务端把它作为“已定位”项列出（不计入数字），而不是清掉筛选或切换集合。

## 只读与权限

**不自行授权两个只读工具，也不使用通配授权。**
ZCode 对插件的 MCP 工具照常执行权限规则，`readOnlyHint` 不会免除审批。插件写数据库或配置给自己放行，就越过了用户的权限决定。
代价：首次使用要用户手动允许两个工具；实测宿主的审批入口不在主页面显示，面板会一直“读取中”直到超时，只能靠 README 和页面提示引导。
重新考虑：ZCode 提供插件声明只读工具的官方机制，或修复审批入口的显示。

**不把 CLI 的 `permission.allowedTools` 当作安装方案。**
在 Desktop 会话里实测它没有放行详情工具，不能写成已验证的解法。

**不自动打开“完整保留模型 I/O”。**
这个设置会增加磁盘占用，而且改的是 ZCode 的行为。插件只说明它能解锁哪些功能，由用户自己决定。
代价：默认设置下看不到移除项、按类别的变化量和正文 Diff。

**不修改系统提示词（不做 dsh 的 Prefix/Suffix 设置）。**
它会改变 Agent 的行为，超出只读观察的范围。

**视图状态只是偏好，不提供授权。**
每次工具调用都重新从宿主元数据绑定会话。保存的选择、展开状态即使指向别的会话，也不会被用来读取数据。

## 数据真实性

**不显示实时上下文占用或上下文窗口百分比（不做 dsh 的 Live / Next Request）。**
插件读的是已经落盘的请求记录，最新一条也只是上一次请求，不是下一次请求的实时状态。把它改名成“当前上下文”会误导用户。
重新考虑：ZCode 向插件提供上下文压力或组成的实时投影。

**不猜内容来源（skill、插件、注入）。**
只按 system、user、assistant、tool、schema 这些角色分类。按正文片段拆来源一定会有错判，而错判比“未细分”更难被发现。
重新考虑：记录里出现结构化的来源元数据。

**不从内容变少推断压缩。**
压缩只以日志事件为准；大小下降只作为观察到的变化显示。只读最近 3 天的日志，所以“没读到事件”也不代表没有压缩。

**上下文事件以 ZCode 会话记录（SQLite 的 `message` / `part` 表）为准，日志只补它没有的类型。**
会话记录覆盖整个会话，不受日志 3 天窗口、请求记录 24 MiB 读取窗口和 32 MB 缓存的限制。每条消息带 ZCode 自己写的 `semantics`（来源、类型、是否发给模型），所以注入按 ZCode 的标签显示（TodoWrite 提醒、Agent 列表、恢复的上下文、后台任务通知等），不按正文猜来源。
- 注入：模型可见、但不是用户自己发的消息，每条一行；Skill 加载来自 `tool` 部分。
- 压缩：来自 `compaction` 和 `timeline` 部分，带压缩前后 token、被摘要的消息数和摘要消息；同一次压缩的日志按命令 ID 或时间重叠去掉。
- 模型切换：来自 `timeline` 的 `model_change`；有它时不再用日志里的模型更新。
- 回退、编辑提问和 MCP 工具注册只在日志里，仍按 3 天窗口读取。
读取只限当前绑定会话，内容和插件已经在读的请求记录是同一份；只用 `json_extract` 取需要的字段，大的工具输出和工具参数不进 JavaScript（标题只取命令、路径等字段的前 160 字，token 估算从前 400 字符的样本按长度放大）。按 `time_updated` 增量读取。插件记得所有消息和 part 的 id，每次有变化就比对数量：删除（ZCode 清理持久化失败的压缩消息时，可能和同一轮的新增抵消）直接去掉；出现从没见过的行（数据库被恢复、行带着更早的时间戳回填）或游标倒退时整体重读。读不到这两张表时退回到只用日志；数据库只是暂时打不开（例如被备份占用）时保留上次的事件。
回退不删除任何行：旧分支留在会话记录里，ZCode 只在会话的 `revert` 字段记下保留的前缀和切点。旧分支上的注入、压缩和模型切换仍按时间留在事件列表里，和趋势里仍保留的旧分支请求一致；但「被摘要的内容」只在当前分支上列出，压缩本身在已回退的分支上时直接说明无法确定，不把旧分支的消息算进去。
压缩状态按 ZCode 写的值显示：进行中、重试中、完成、失败、已中断、已跳过；认不出的状态显示“未知”，不归为完成。
普通的工具调用和结果不单独成为事件：它们已经在概览的「输入」行和「仅变化」里。0.3.5 之后一度按请求记录推断“注入”和“大块内容”，换成会话记录后去掉：推断只能覆盖缓存里的几步，大块内容回答的是趋势图已经回答的问题。

**事件按原文定位到浏览器里的那一项，定位不到就显示原文。**
注入在它之后的第一个主请求里找：Skill 按工具调用 ID，其他按原文完全包含（取最后一处，因为提醒会重复），不做相似度匹配，也不只比开头——TodoWrite 提醒的固定开头就超过 300 字。超过 4000 字的正文按长度和 SHA-256 摘要核对（全文逐条读出计算，超过 2 Mi 字符不核对）；核对不了就不定位。“之后的第一个”要求它和前一步之间没有被跳过的记录（同一文件、同一连续段）；它是最早一条可读记录时，要求文件从头读起、中间没有损坏行、超大行或淘汰。找不到对应请求或里面没有这段原文（请求记录已轮转、超出读取窗口、更早的历史未加载、中间有缺口）时，事件不指向任何一步，点击直接展开会话记录里的原文，不把邻近的一步当成它。
压缩选中之后的第一步、以之前的一步为基线：能对比时切到「仅变化」；不能对比时写明原因并打开 ZCode 的续接摘要。被摘要的内容从会话记录按需读取，按提示、回复、思考、工具调用逐项列出——默认记录（tail）下这是唯一能看到“压缩去掉了什么”的地方。模型切换打开请求概览。MCP 工具注册进入事件焦点：注册后的第一步、以注册前的一步为基线，只看工具名以 `mcp__` 开头的工具定义；注册之后没有可读取的请求时不跳到别的步骤，只在事件行里说明，并把“在最新一步查看”作为写明了的选项。早于已加载步骤的事件先加载更早的步骤再定位。

**不强行把 SQLite 用量和请求记录逐条对应。**
`logical_request_id` 和记录里的 `requestId` 没有被证明是同一个标识，硬连可能按网络重试次数把用量算多。两者分成“用量页”和“请求诊断”两条轨道，同一条记录里自带的 provider usage 作为这次 attempt 的实际用量单独显示。
记账用到的会话记录大小不改变这一点：它们只经 ZCode 写入的 `assistant_message_id` 和工具调用 ID 连到条目，不把 SQLite 的行和请求记录对应起来。

**默认记录（tail）下不猜移除了什么。**
ZCode 默认只记录每次请求最近 64 条消息。之后的请求按 ZCode 自己未裁剪的上一条写增量（delta），插件把它接在已记录的尾部后面，仍标为不完整。新增内容可以由入场标记推出，移除项无从得知，界面直接说明，不做对比。

**普通消息的替换不做正文 Diff。**
只有工具结果 ID 或 schema 名称唯一时才配对“替换前 / 替换后”。按文本相似度或位置配对，很容易把两条无关消息说成同一条的修改。

**已淘汰或轮转的内容不恢复，脱敏图像不显示缩略图。**
只展示真实保留下来的内容。

**步序号是相对的；入场标记追不到时显示“更早”。**
序号从当前能读到的第一条记录开始数。遇到记录缺口、文件重置或压缩时不往前猜步骤。

**工具调用次数读不到时显示未知，不显示 ×0。**
×0 的意思是“确认从未调用”，这是可以据此删除工具定义的结论，不能用来表示数据缺失。

**不估算费用。**
需要按版本维护模型价格、别名和计费口径，还要联网更新。价格不明时报出的数字是假的。

## 大小口径

**请求的大小以 provider 上报的实际输入为准；条目和类别按实测增量记账，估算只在一个实测总量里分份额，或在无从实测时代替。**
同一序列（同一文件的连续段、同一来源、同一模型）里，相邻两次请求的实际输入之差，加上离开内容已记下的大小，正好是新进入内容的大小。新回复按生成它的那次响应的输出 token 记，前提是先用工具调用 ID（文本回复用整段回复正文）证明它就是那次响应，而且这个输出小于这一步的增量、给其余新增内容留出位置；单独进入的回复直接按增量记。这一步其余的新增内容只有一项、而且离开的内容都是实测的时候，它就是实测值；几项一起时，按估算分这一步的实测增量；离开的内容里有估算份额时，结果也只是份额。同样的内容在同一模型、同一来源下再次出现时，沿用测过的大小，前提是放得进这一步的增量。实测值都不小于 1 token。增量里对不上、但在容差内（16 token 或 0.2%）的部分作为余量单独记着，余量超过容差就整次重新起账。序列开头的那次请求没有增量，总量按估算分给各项，沿用的大小和 ZCode 会话记录测过的回复与单个工具结果除外：`model_usage.assistant_message_id` 由 ZCode 写入，把每次请求和它产生的助手消息连起来；会话记录只配对同一来源里真正相邻、模型相同、中间没有压缩或模型切换的两次请求，工具结果还要求请求里的内容和会话记录里的输出等长（内容被清理或改写过就不套用）。已知的大小要是给其余条目留下的不到估算的 30%，就整体不用。实测的大小和变化不带 ≈；估算和按估算分出的份额带 ≈，提示里写明分的是哪个实测总量。界面的大数字始终是实际输入，「实测 N%」是能实测的部分占多少（向下取整）。
本机验证：162 个完整记录文件、3,136 步里只有 1 步对不上；会话记录推出的 404 个工具结果和 583 条回复，和请求记录推出的完全一致。会话记录认为“一步只新增了一个工具结果”的 407 步里，有 3 步的请求还临时注入了提醒或工具定义（会话记录里没有），这时它们会被算进那个工具结果。工具结果的长度核对在本机 94% 的情况下成立，不成立的是错误结果和图片，这些不会从会话记录补值。
代价：一步同时新增多项时，各项只是估算份额；系统提示词和工具定义从不出现在增量里，永远是份额；冷读只读文件末尾 24 MiB，之前进入的内容只能靠会话记录和沿用补上。每次刷新多一条 SQLite 汇总查询，行有变化时再读一次（本机约 2 ms），冷读的扫描多约 4%–9%。
防护：输出经常超过下一步增量的模型不回传全部输出（例如隐藏推理；本机 GPT 系列 20%–24% 的步骤如此）。至少 10 次检验里超出 3 次以上、比例超过 5% 时，之后不再按输出记它的回复，之前为它记下的大小也不再沿用，当前请求整次重新起账；会话记录按同样的检验对整个会话里的每个模型单独判断，判断结果在读第一条记录之前就生效。只检验离开内容都是实测的步骤。隐藏推理比同一步的工具结果还小时，单步检验发现不了；本机 GPT 会话靠会话级的判断覆盖，不到 10 步的短会话仍可能把这部分算进回复。默认记录（tail）的总量包含没记录的消息，从不拆分：窗口只在重叠部分逐条一致、两条记录之间没有压缩时才算续接，只测重叠之后新增的消息，滑出窗口的内容转入「更早消息（未记录）」。
两次请求换了模型时，分词器不同，变化量不按实测给出。类别的变化只算进入和离开的内容，同一内容在两边的份额不同不算变化；全部进入和离开的内容都是实测时才不带 ≈。

**不内置分词器，也不按模型调估算系数。**
不同模型的分词器差别很大；内置多个分词器会显著增大离线包，而且结果依然只适用于部分模型。记账之后估算只用来在实测总量里分份额，按比例分配时统一的系数会抵消，调系数几乎没有作用。本机数据也说明没有通用的系数：单个工具结果的“实际/估算”中位数在 Claude 上是 1.53，在 GLM 上是 0.94；换成 ZCode 内置公式（ASCII 约 3 字符 ≈ 1 token）在 Claude 上更准，在 GLM 上反而高估约 40%。
0.3.4 起，英文和代码约 4 字符 ≈ 1 token，中日韩文字约 1.5 字 ≈ 1 token；之前一律按 4 字符计，中文内容显得偏小。

**不用实际输入按统一比例缩放各类别的估算。**
默认记录下，实际输入里包含没有被记录的更早消息。按比例缩放，会把这部分大小摊到已记录的类别上，同时把“估算”伪装成“实测”。即使记录完整，比例也不稳定：每次请求的估算与实际之比在 0.56 到 2.36 之间（中位 0.72），相邻两步之间的增量之比在 0.4 到 1.7 之间（10% 到 90% 分位），统一系数会把一类内容的误差转嫁给别的类别；本机中位约 6% 的 token 会因此分错类别。记账只在一个实测总量内部分配，不跨请求缩放。

## 读取范围与性能

**所有读取都有上限，超出部分不可见。**
冷读文件窗口 24 MiB，单次扫描和单行各 8 MiB；每个文件缓存 120 条记录，最多 8 个会话、合计 32 Mi 字符；worker 堆 256 MiB。趋势每页 60 条，最多往前翻 4 页；正文每块 12k 字符，正文查找最多导航 100 处；用量页为 30 天、时间线 80 条。
代价：超长会话的早期历史看不到。换来的是插件在任何会话上都不会拖慢 ZCode 或耗尽内存。

**正文 Diff 是“共同前后缀之间的替换块”，不是最小行编辑序列。**
线性时间、有上限；最小 LCS Diff 在大工具结果上开销不可控，侧栏里也难以阅读。

**复制只复制当前这一块；Markdown 只支持标题、段落和代码。**
捕获内容一律按纯文本或受限 Markdown 显示，不执行其中的 HTML。

**服务端不缓存无变化的读取（0.3.4 实测后放弃）。**
32 MiB 的真实会话，无变化时一次刷新约 7 ms，其中 SQLite 约 4 ms。按文件修改时间缓存会引入读到过期用量的风险，收益只有几毫秒。

**超时的读取如果已经在执行，就让它跑完，不重启 worker。**
重启会丢掉解析缓存，下一次冷读可能再次超时，形成循环。还没开始执行的读取则直接跳过。

**用轮询，不用推送。**
面板只能主动调用 app-only 工具读取数据，目前没有验证过宿主有可用于此的推送通道。0.3.4 起数据无变化时逐步放慢到 10 秒，面板可见、获得焦点或鼠标移入时立即刷新。

## 面板形态和尺寸

上下文面板是会话右侧面板里的一个 Tab：宽度大约 320–560 CSS px，和其他 Tab 共用同一块区域，而且只属于打开它的会话。
ZCode 的 `fullscreen` 显示模式指的就是这个侧栏，不是中央大页面；请求 `inline` 也不保证有卡片接管。
dsh-context 有一部分功能依赖宽屏的中心页，硬搬进来要么挤坏，要么只剩装饰。下面这些不做，主要原因是面板放不下或用起来不顺，而不是缺数据。

**不做两列布局（趋势和浏览器并列、列表和正文并列）。**
560 px 分成两列，每列不到 280 px，类别行的名称、条数、大小和占比放不进一行。改为单列从上到下：概览、趋势、浏览器、压缩事件。
重新考虑：ZCode 提供经过验证的宽工作区页面。

**正文 Diff 只做单列，不做左右对照。**
前后两段正文各占半宽，长行全部折行，反而更难对比。单列只高亮变化块，前后各留两行上下文。

**不做 DNA 元素条带。**
长会话一次请求有几百个上下文元素，在几百像素宽的条带里每个元素只有一两个像素，看不清也点不中。按类别折叠、按大小排序能更快找到大块内容。
数据上也有限制：记录里的 SDK 消息和 provider 请求体是两种表示，条带顺序不能冒充 provider 收到的原始顺序。

**不做跨会话 Insights（时间范围、热力图、会话卡片、跨会话搜索）。**
这是工作区级的仪表盘，需要中心页的面积；而这个 Tab 属于单个会话，在一个会话的侧栏里展示别的会话也不符合预期。
读取整个工作区还需要显式扩大读取范围，不能借当前会话的绑定静默读取。

**不做子代理网络图（dsh 的 Fleet）。**
节点关系图在窄栏里放不下，标签会互相重叠。父子会话将来可以用列表展示，前提是先设计好授权范围；实时运行状态目前没有验证过的来源。

**不做时间组成图和时长曲线。**
等待、生成、工具、开销的分段条再加更细的生成阶段，在窄栏里层层堆叠，密度过高；趋势区已经有总量 / 变化、步骤 / 轮次两组切换。
数据上也有缺口：并行工具的耗时不能直接相加成墙钟时间，没有流式阶段数据就拆不出思考和正文耗时。用量页只列每次请求的耗时。

**不做额外入口（中心页、/context 命令、偏好设置卡）。**
ZCode 给插件的界面入口就是会话侧栏的 Tab；dsh 的一级导航和命令入口在 ZCode 里没有对应的可调用接口。少数偏好直接放在用到它的地方，比如趋势上的切换按钮。

**趋势只铺开最近一屏可点击的柱子。**
不把整个会话压成一排点不中的细线；更早的步骤横向滚动或翻页查看，「自适应」纵轴按可见范围缩放。

**顶部不堆累计用量卡片，会话 ID 不常驻一行，解释性文字收进底部说明。**
窄栏的第一屏只有几百像素高，要留给“这一步多大、变了什么”。

## 主路径和信息密度

面板只服务一条主路径：哪一步变大了、多了什么内容、点开看正文。帮不上这个问题的功能，即使有数据也不放进来。

**只保留一种布局。**
0.2 有“诊断优先 / 浏览优先”两种布局偏好，0.3.0 重写侧栏时去掉了浏览优先。卡片布局里的趋势足够紧凑，浏览器紧跟在后面；第二种布局的收益抵不过它带来的成本：每种宽度、主题和语言都要多验证一遍。

**条目在列表里行内展开，不跳到单独的详情页。**
0.2 点开条目会进入详情页，靠“返回”回到列表。0.3.0 改成行内展开：读正文时仍能看到它属于哪个类别、前后是什么，也不需要来回恢复滚动位置。

**首页是请求诊断，30 天累计用量放到次级页面。**
累计数字回答不了“为什么这么大”。

**标题生成、压缩等辅助请求不进趋势。**
它们仍可在下拉框里选中，但混进趋势会让变化柱和相邻柱没有可比性。

**展开条目阅读时暂停跟随最新请求。**
新请求到来只提示“有 N 个新请求”，不会把正在读的正文切走。

## 暂缓：缺数据或证据

下面这些放得进面板，也在主路径附近，卡在数据是否可信：

| 功能 | 暂缓原因 |
|---|---|
| 文件活动（读、写、搜索过的文件） | 只能基于明确的工具名、参数和结果提取；任意 shell 命令解析不出可靠的文件事实 |
| 工具耗时、错误与重试 | 只能用可信字段，并区分逻辑请求和实际模型调用，避免重复累计 |
| 子代理的独立用量 | session 表有 `parent_id`，但要先确定读取子会话的授权范围 |
