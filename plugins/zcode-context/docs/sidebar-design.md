# Context 侧栏产品与界面设计提案

> 历史快照（0.2 的设计提案）。现行交互规则见 [产品决策与取舍](decisions.md)；本文不再更新。

日期：2026-10-12。目标：在官方会话侧栏内提供与 dsh 类似的单会话诊断路径。
本提案是下一版设计，不代表 0.1.1 已实现这些能力；交互草图使用示例数据。

## 当前验收结论

ZCode 已升级至 3.15.1.8093。官方 CLI 校验和隔离安装通过。
真实 Electron 面板完成 MCP Apps 握手，绑定到客户端创建的会话；该会话的 SQLite 用量和 traj 可读。
测试会话经真实 Agent loop 调用本地模拟模型。数据库记录主请求输入 5,250、输出 32，标题请求输入 5,100、输出 32；面板显示合计输入 10,350、输出 64，与数据库一致。
用户在测试窗口操作后反馈没有出现问题，基础接入可以作为下一版的起点。
多窗口、重启、所有压缩场景等完整验收尚未完成；不能把基本接入通过写成全部桌面测试通过。

桌面调试截图曾出现合成裁切，页面 DOM 内部宽度与样式正常；系统截图因窗口被遮挡无法核验。这不作为已确认的插件 CSS 缺陷。
测试隔离曾遗漏 CLI 默认用户配置路径，本次新增的正式配置项已经撤销；随后改用完整子进程配置隔离。没有改官方源码和用户真实会话数据。
测试进程已停止。

## 产品主轴

用户进入面板后，应在同一个所选请求上完成四件事：

1. 看这一请求带了什么、约多大。
2. 看与上一请求相比什么增加或消失。
3. 判断哪些变化有压缩日志证据。
4. 点开具体系统指令、schema、消息或工具结果。

面板首页从“30 天累计用量”转向“最近记录的请求诊断”。累计用量仍保留在清晰的次级入口。
选择历史请求后暂停跟随最新记录，新请求到来显示“有新请求 / 回到最新”。不要自动把正在读的正文切走。

## 默认布局：诊断优先

建议以 380–460 CSS px 为主要设计宽度，兼容 320–560 px。

### 第一层：请求与变化概览

- 顶部简洁标题与“用量”入口；会话 ID 不常驻占一行，需要时在信息区显示并复制。
- 紧凑的上一请求 / 请求选择器 / 下一请求；明确“最近已记录”或“已固定历史请求”。
- 一个主数字：所选输入组成的估算量。其旁是相对上一快照的变化，不展示未确认的实时窗口百分比。
- 实际 provider input/output/cache 若该 traj 记录保留 usage，就作为同一 attempt 的独立字段显示；未知则显示未知。
- 约 110–140 px 高的趋势区域，固定类别颜色和少量轴刻度。
- 默认最近 8–12 个可点击请求，其余通过有界历史导航访问；不把全会话压成不可点击的细线。
- 总量 / Delta 是主要切换；回合粒度和时长曲线放到次级选项。

### 第二层：组成 / 变化 / 事件

这三个视图共享所选请求，放在趋势之后。

组成：

- 首层为可折叠类别，每行放名称、条数、估算大小和占比。
- system/user/assistant/tool/schema 使用固定配色；无证据时不强拆 skill、插件或注入来源。
- 默认展开最大的类别；按大小排序，最快看到大工具结果。
- 单条内容用可读摘要和大小命名，如 `Read · src/cache.ts`；原始 key/requestId 放到详情。
- 搜索覆盖已加载的快照范围，搜索范围与缺口可见；不只搜索当前 40 项分页。

变化：

- 先显示总变化，再按类别展示增减和新增/删除条数。
- 新增/删除项能打开对应快照的正文；匹配的替换内容可以进一步展开正文 Diff。
- 默认比较同来源上一完整快照；基线与缺口始终可见。
- 用单列高亮变化块适配窄栏。较宽时才提供双列 before/after，避免两段文本被压成细条。

事件：

- 压缩类型、完成/失败、时间、turnId、日志记录的原因转成可读标签。
- 事件可以定位压缩前后已捕获的输入。精确匹配有证据才定位到具体请求，否则显示时间范围。
- 内容下降属于观察事实，日志确认的压缩属于原因证据，保持两者区别。

### 第三层：内容详情

点击条目后用详情页占用侧栏主体，顶部保留“返回”、所选请求和条目类型。

- 工具结果显示调用名称、已记录参数、状态、正文；有可靠 toolCallId 才配对调用与结果。
- 系统指令、普通消息和 schema 各用合适的可读表示，保留原始数据入口。
- 正文提供复制、搜索、行数、Raw/Markdown；大内容按块读取。
- 内容 Diff 默认统一单列，给出来源快照和基线。
- 返回恢复请求、类别、筛选、展开与滚动位置。
- 不将完整正文长期夹在请求列表底部；避免用户为读一个工具结果先滚过几十条请求。

## 另一种布局：浏览优先

请求选择与大小概览保持一致，趋势默认折叠，搜索和分类列表在第一屏。
适合频繁查系统指令、工具 schema 和日志内容的人。

它能减少进入正文的操作，但输入变化的故事不如诊断优先直观。建议作为查看偏好，而非替代默认诊断路径。
交互草图包含两种方案，便于比较。

## 宽度与视觉约束

| 宽度 | 排布 |
|---|---|
| 320–379 px | 单列；控制区允许两行；次要模型/时间收起；正文和变化始终单列 |
| 380–519 px | 标准单列诊断视图；类别元信息保持同一行；正文钻取 |
| 520–560 px 及更宽侧栏 | 增加摘要和工具参数信息；仍不强行并列趋势与浏览器 |
| 将来有经验证的宽工作区页面 | 才采用 dsh 类似的两列布局；当前不以此为完成核心功能的前提 |

- 正文维持可读字号，通过折叠和导航控制密度，不整体缩小页面。
- 固定类别颜色、统一数字格式；类别颜色只用于图形、标记和图例。
- 减少大面积卡片，使用轻分隔和紧凑行；顶部不堆四个累计用量卡片。
- 常驻关键摘要即可，解释性长段落进入提示或数据说明。
- 布局看容器的 CSS 宽度，不依赖 Windows 截图中的物理像素数。
- 窄栏只保留一条主要垂直滚动路径，长正文按需加载。

## 当前宿主约束

已读本地官方 UI_PLUGIN.md 及 buildPluginUiHostContext 实现：

- `fullscreen` 在当前 ZCode 中表示会话侧栏，不等于中央全屏页面。
- surface 请求 `inline` 也不保证有内联卡片接管。
- 因此不能把“点开独立全屏窗口”作为窄栏读正文的必需路径。
- 首版所有关键操作在侧栏内完成；宿主允许用户拉宽时自然适配。

SQLite 用量与 traj attempt 保持两条明确的数据轨道。共享选择以 traj 快照 key 为准，不强行把 SQLite 图柱连到未经证明的 traj request ID。

## 功能与实施顺序

### v0.2 核心闭环

- 所选请求模型与跟随/固定状态。
- 分类堆叠趋势、Delta、压缩区间提示。
- 历史组成同步、分类列表、摘要、排序、搜索、大来源定位。
- 工具/消息/schema 详情、正文阅读、分类变化和 Diff。
- 可读压缩事件与前后快照导航。
- 查看偏好和页面重建恢复。

### 后续扩展

- 单会话 turn_usage/tool_usage 统计、TTFT 与工具耗时。
- 有明确参数/结果证据的文件活动。
- 依据 parent_id 的子代理关系与独立用量。
- 最后考虑工作区级 Insights、DNA 元素条带、费用估算。

核心闭环完成时，用户应能实际回答：“第几次请求变大？主要增加了哪类内容？具体是哪个工具返回？压缩前后移除了什么？”

## 建议的内部状态与验证

- UI 共享 session binding、selected snapshot key、baseline key；tab、expanded category、search、detail cursor 和滚动位置是视图状态。
- 服务提供独立 timeline/overview、可分页且可过滤的元素摘要、正文分块、Diff 与事件证据。
- 提供窄栏组件，而非继续把所有渲染逻辑追加到现有 app.mjs 的单个 render 中。
- mockup 的示例数据不接真实数据库，不将演示完成当作功能已实现。

验收重点：选 R12 后所有相关视图均为 R12；刷新不抢走选择；返回不丢展开位置；缺基线不产生虚假的负 Delta；320/360/420/520 px 无横向溢出；长正文按块加载；主题与语言切换保持选择。
